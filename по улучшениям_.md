## Критично: sessionID всё ещё течёт

В `experimental.chat.messages.transform` session ID не приходит из `input`; вместо него используется глобальный `lastSessionID`.  Этот `lastSessionID` обновляют другие hooks (`chat.params` и `tool.execute.after`), поэтому при параллельных агентах или обычном multi-session использовании transform может проверить сообщения сессии A по ledger сессии B.[^1]

Проблемное место по сути такое:

```js
let lastSessionID = null;

// ...
experimental.chat.messages.transform: async (input, msgOutput) => {
  const sessionID = lastSessionID;
  // ...
}
```

Это нужно исправить одним из двух способов:

1. **Правильный вариант:** получить `sessionID` из реальной структуры `input` или `msgOutput` в этом hook и использовать только его.
2. **Если API hook не отдаёт session ID:** вообще не делайте completion/laziness-проверку в `messages.transform`; перенесите её в hook, где гарантированно есть `input.sessionID`.

Пока этот участок не исправлен, первоначальная P0-проблема изоляции сессий устранена лишь частично.[^1]

## Критично: completion gate обходится `echo`

Проверка считает верификацией **любой** `bash`-tool call после `write`/`edit`, если у него `exitCode === 0` и отсутствует `hasError`.  Это означает, что агент потенциально сможет формально закрыть gate командами:[^1]

```bash
echo "done"
pwd
git status --short
```

Ни одна из них не проверяет код. Более того, если OpenCode не передаёт exit code в `metadata` и output не содержит распознаваемую строку, `exitCode` может быть `null`, и настоящая успешная тестовая команда тоже не будет засчитана.[^1]

Нужно сохранять саму выполненную команду и классифицировать её:

```js
function isVerificationCommand(command = "") {
  return /\b(
    npm\s+(test|run\s+(lint|test|typecheck|build))|
    pnpm\s+(test|lint|typecheck|build)|
    yarn\s+(test|lint|typecheck|build)|
    pytest|
    ruff\s+check|
    mypy|
    pyright|
    tsc(\s|$)|
    go\s+test|
    cargo\s+test|
    gradle(w)?\s+test|
    mvn\s+test
  )\b/ix.test(command);
}
```

И в gate требовать именно:

```js
entry.tool === "bash" &&
entry.exitCode === 0 &&
entry.isVerification === true
```

Для гибкости добавьте project-level allowlist, например в `fablize.config.json`:

```json
{
  "verificationCommands": [
    "npm run check",
    "npm test",
    "pytest -q",
    "ruff check .",
    "python -m mypy src"
  ]
}
```

Так GLM сможет проверять проект реальными командами, а не «успешно выполнить любую команду».

## Существенно: пустой ledger не блокирует done

Системный prompt утверждает: «Empty ledger done blocked», а `getLedgerSummary()` пишет, что завершение без tool calls заблокировано.  Но функция `checkCompletionGate()` при пустом ledger сразу возвращает `null`:[^1]

```js
if (!text || !ledger || ledger.length === 0) return null;
```

То есть модель может ответить «готово», вообще ничего не сделав, и плагин фактически ничего не заблокирует. Это расхождение между заявленной и реальной логикой.[^1]

Исправьте начало функции:

```js
function checkCompletionGate(text, ledger = []) {
  if (!text || !DONEPATTERNS.some((re) => re.test(text))) {
    return null;
  }

  if (ledger.length === 0) {
    return [
      "COMPLETION BLOCKED:",
      "The response claims completion, but this session has no tool evidence.",
      "Inspect or execute the requested work, then report the result."
    ].join(" ");
  }

  // Дальше: проверка последнего write/edit и valid verification.
}
```

Важно: для чисто разговорных задач («объясни концепт», «сравни два подхода») такое правило будет вредным. Поэтому включайте строгий completion gate только для режимов `create`, `debug`, `audit`, financial и будущего `coding`, но не для `default`/`creative`.

## Средний риск: old anti-laziness остался

Вы правильно добавили `DONEPATTERNS` и gate, но старая функция `detectLaziness()` и `LAZYPATTERNS` всё ещё активны.  Она по-прежнему ловит естественные фразы вроде `I'll do`, `let me check`, `I'll run`, а затем добавляет на следующем шаге жёсткий alert о том, что модель «пообещала без выполнения».[^1]

То есть вы заменили часть механизма, но ложные срабатывания старого остались. Рекомендую удалить `LAZYPATTERNS` целиком либо оставить только реально рискованные конструкции:

```js
const UNSUPPORTED_CLAIMS = [
  /\b(this should work|this will likely work)\b/i,
  /\b(готово|исправлено|реализовано|решено)\b/i
];
```

Не надо наказывать модель за намерение воспользоваться инструментом. Наказывать нужно лишь за **заявленное завершение или неподтверждённый результат**.

## Средний риск: неверная классификация ошибок

`hasError()` ищет подстроку `error`, `failed`, `traceback` и другие слова в любом tool output.  Поэтому успешный тест вполне может попасть в ошибку, если output содержит, например:[^1]

```text
0 errors
No failed tests
error handling tests: passed
```

Это испортит ledger и может заставить модель не засчитывать успешную верификацию. Используйте сначала exit code как главный источник истины:

```js
function hasError(output, exitCode) {
  if (exitCode !== null && exitCode !== undefined) {
    return exitCode !== 0;
  }

  const text = String(output || "");
  return /\b(traceback|exception|fatal error|command not found)\b/i.test(text) ||
    /\b(failed|error)\b/i.test(text) &&
    !/\b(0 errors|no errors|0 failed|all tests passed)\b/i.test(text);
}
```
