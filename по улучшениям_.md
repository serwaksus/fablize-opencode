P0: ledger.length на первой сессии
В system.transform остаётся:

js
const ledger = ledgers.get(sessionID);
const hasWrites = ledger.length > 0 &&
  ledger.some((e) => e.tool === "write" || e.tool === "edit");
При первом обращении к сессии ledgers.get(sessionID) возвращает undefined, потому что ни одного tool call ещё не было. Тогда обращение к ledger.length выбросит TypeError.

Исправьте строго так:

js
const ledger = ledgers.get(sessionID) ?? [];

const hasWrites = ledger.some(
  (entry) => entry.tool === "write" || entry.tool === "edit"
);
В messages.transform тоже лучше нормализовать значение:

js
const ledger = ledgers.get(sessionID) ?? [];
Хотя countWritesInLedger(ledger) и hasRiskyFileChange(ledger) теперь сами имеют fallback, единый вариант устранит случайные будущие ошибки.

P1: diff evidence засчитывается даже при ошибке
Сейчас reviewEvidenceSeen становится true при любой bash-команде, которую распознаёт isDiffReviewCommand():

js
if (input.tool === "bash" && isDiffReviewCommand(command)) {
  stateOf(sessionID).reviewEvidenceSeen = true;
}
То есть git diff с ошибкой — например, агент не в Git worktree или команда завершилась с ненулевым exit code — всё равно разрешит review verdict.

Добавьте проверку успешности:

js
if (
  input.tool === "bash" &&
  exitCode === 0 &&
  !errorFlag &&
  isDiffReviewCommand(command)
) {
  stateOf(sessionID).reviewEvidenceSeen = true;
}
И лучше разделить два вида доказательства:

js
function isDiffCheckCommand(command = "") {
  return /^git\s+diff\s+--check\b/i.test(command.trim());
}

function isDiffInspectionCommand(command = "") {
  return /^git\s+diff(?:\s|$)/i.test(command.trim()) &&
    !/^git\s+diff\s+--check\b/i.test(command.trim());
}
Для high-risk diff разумный критерий:

git diff --check успешно прошёл;

выполнен git diff для содержательного чтения изменений;

модель дала verdict.

Это исключит формальное «я посмотрел diff», когда был лишь запуск проверки whitespace.

P1: blind spot и план остаются soft prompts
Новая версия правильно распознаёт, что модель фактически сформулировала blind-spot pass или план, через hasBlindSpotCompletion() и hasPlanMarkers(). Но после первого write оба статуса всё ещё принудительно переводятся в completed/provided:

js
if (st.blindSpotRequested && !st.blindSpotDone) {
  st.blindSpotDone = true;
}

if (st.planRequested && !st.planProvided) {
  st.planProvided = true;
}
Это не блокирует релиз, потому что жёстко запрещать первый edit — действительно риск зациклить агента. Но в таком виде это не enforcement, а подсказка.

Минимальная качественная доработка без блокировки работы:

js
blindSpotBypassed: false,
planBypassed: false,
js
if (st.blindSpotRequested && !st.blindSpotDone) {
  st.blindSpotBypassed = true;
}

if (st.planRequested && !st.planProvided) {
  st.planBypassed = true;
}
Перед финальным done для risky/complex задачи добавляйте один короткий gate:

text
FINAL ACCOUNTABILITY REQUIRED:
The implementation proceeded without a recorded blind-spot pass / plan contract.
State the assumptions, actual scope, acceptance checks, and residual risks.
Так вы сохраните агенту возможность действовать, но не дадите ему выдать сложную работу за полностью проверенную без описания допущений.
