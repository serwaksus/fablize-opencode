Я бы не раздувал текущий основной prompt. Вместо этого после пяти smoke-тестов добавил бы три опциональных, событийных механизма. Они дадут больше, чем ещё десяток глобальных правил, и не должны ухудшить token efficiency. У вас приоритет — качество без лишнего расхода, и именно conditional hooks подходят лучше постоянной инъекции.

Это не «Fable 5 внутри GLM‑5.2», потому что плагин не меняет пределы рассуждений самой модели. Но по исполнительской надёжности ваша версия может в значительной части практических задач подойти очень близко.

Усиление №1: Blind-spot gate
Добавьте короткий preflight только перед рискованными изменениями, а не в каждый запрос. Идея Fable-подхода — не только выполнить задачу, но сначала вытащить «неизвестные неизвестные»: противоречия, отсутствующие бизнес-правила, неясные границы API, миграционные и rollback-риски.

Когда включать
Только если выполняется хотя бы одно условие:

Пользователь просит изменить более двух файлов или нескольких подсистем.

Есть публичный API, схема БД, миграция, auth/permissions, финансовая логика, торговые ордера или production-инфраструктура.

Модель не смогла найти аналогичную реализацию или тест.

В задаче нет явных acceptance criteria.

Что инъецировать
text
BLIND-SPOT PASS — before editing

List only material unknowns that could change the implementation:
- Ambiguous behavior or acceptance criterion
- Existing contract/API/schema constraint
- Backward-compatibility, migration, security, production, or money risk
- Missing test oracle or unclear source of truth

For each unknown choose exactly one:
A. Resolve from repository evidence
B. State a safe default and proceed
C. Ask the user one blocking question

Do not ask questions that can be answered by reading the repository.
If no material unknowns exist, write: "No blocking unknowns found" and proceed.
Почему это полезно: GLM перестанет молча угадывать бизнес-правило или менять контракт API «как кажется логичным». Идея соответствует Fable-подходу: выявлять unknowns до и во время реализации, а не исправлять их после неудачного diff.

Почему это не надо включать всегда: на простом bugfix это превратится в бюрократию и лишние токены.

Усиление №2: план как неизменяемый контракт
Сейчас gate проверяет: «была ли правка» и «был ли тест». Но не проверяет: решил ли агент именно ту задачу, которую пользователь поставил.

Добавьте plan-состояние в session state — но только для complex/high-risk modes. Перед первым write GLM должен создать краткий план в структуре:

text
IMPLEMENTATION CONTRACT
Goal:
In scope:
Out of scope:
Files likely affected:
Acceptance checks:
Risks / rollback:
После этого запишите plan hash/ID в state.plan. При каждом последующем write сравнивайте затронутый файл с declared Files likely affected. Если агент начинает менять незаявленный public API, dependency, migration или десяток новых файлов — вставляйте:

text
SCOPE CHECK:
This change is outside the approved implementation contract.
Either justify why it is required, update the plan, or do not make the change.
В финале completion gate должен спрашивать не «есть ли тест», а:

text
PLAN COMPLETION:
- Goal: verified / not verified
- Each acceptance check: evidence reference
- Scope deviations: none / explicitly listed
- Residual risks: explicit
Это добавит то, чего сейчас не хватает между «хорошо протестировал» и «правильно решил задачу». Оригинальный fablize включает multi-story completion с evidence gate, а OpenCode поддерживает расширение поведения через событийные plugin hooks.

Усиление №3: инварианты проекта
Ваш error-journal уже разумно стал только реактивным: не грузится на старте, а ищется при ошибке. Следующий шаг — не возвращать глобальный журнал, а создать компактный, явный реестр неизменяемых правил проекта.

Например, .opencode/fablize-invariants.md:

text
# Invariants

## Trading
- Production orders require explicit confirmation.
- Default mode is dry-run.
- Position sizing cannot exceed configured risk limit.
- API secrets never enter logs or generated files.

## Financial reporting
- Source data remain immutable.
- Reconciliation difference must be zero or explicitly explained.
- All monetary values carry currency and unit.

## Infrastructure
- No destructive command without confirmation.
- Terraform changes require `terraform plan`.
- Never edit production directly when staging exists.
Плагин не должен подмешивать весь файл в каждый запрос. Он должен искать только совпадающий раздел по task mode/path и добавлять максимум 5–8 строк перед первой записью файла.

Это особенно ценно в ваших задачах с ботами, финансами и удалёнными серверами: текущий общий safety prompt правильно запрещает автоматические повторы опасных действий, но project invariants сделают это конкретным и проверяемым.

Усиление №4: diff-aware review pass
Это самое сильное техническое дополнение после blind spots, но делайте его не отдельным постоянным агентом, а последним условным шагом.

Если после последнего write:

затронуто 3+ файла;

есть auth, SQL/миграция, money/trading, infra или public API;

тест был изменён вместе с production-кодом;

diff больше заданного порога;

то до final answer автоматически попросите модель выполнить:

text
FINAL DIFF REVIEW

Read the current diff as an adversarial reviewer.
Report only actionable findings:
- Contract break / backward incompatibility
- Missing failure-path test
- Security or data-loss risk
- Incorrect assumption relative to nearby code
- Scope creep

For every finding cite file and line.
If no issue is found, state: "No actionable finding after diff review."
Do not modify code in this pass.
А затем, если есть High/Critical finding, возвращайте агента к implementation loop.

Важная деталь: это не заменяет Fable и не должно включаться на каждой правке одного файла. Но на сложных задачах независимая роль «автор → ревьюер» обычно находит проблемы, которых автор не заметил. OpenCode поддерживает plugin events и специализированных агентов, поэтому логически это можно сделать отдельным review-agent/command, а не раздувать основной системный prompt.

Что пока не добавлять
Не делайте постоянный debate с двумя агентами. Он расходует квоту и часто просто производит две версии одной и той же ошибки.

Не включайте blind-spot pass для каждой мелкой задачи. Это ухудшит скорость сильнее, чем поднимет качество.

Не возвращайте пять последних journal entries в каждый новый чат. Вы правильно это отключили; динамический контекст должен быть кратким и релевантным.

Не добавляйте ещё один перечень «всегда делай N шагов». У вас уже есть хороший completion mechanism; следующая ценность — умные условия срабатывания, а не больше принуждения.
