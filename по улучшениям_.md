# исправления внесены, смотри

Да, версия стала заметно лучше: вы закрыли все три прежние P0-проблемы на уровне замысла — убрали глобальный `lastSessionID`, добавили блокировку `done` при пустом ledger в рабочих режимах и перестали засчитывать произвольный успешный `bash` как проверку. Появился отдельный `coding`-профиль с правильным контрактом: изучить ближайшую реализацию и тесты, ограничить diff, после последнего изменения запустить минимально релевантную проверку и честно назвать непроверенные риски.[^1]

Но обнаружился один **новый блокер**, из-за которого completion gate может начать блокировать даже реально успешные тесты.

## P0: проверяется title, не команда

`isVerificationCommand()` получает `title`, который формируется так:

```js
const title = output?.title ? output.title : input.tool;
```

а затем вызывается:

```js
isVerification: input.tool === "bash"
  ? isVerificationCommand(title)
  : false
```

То есть классификатор, вероятно, видит `"bash"`, `"Bash"` или короткий UI-title, а **не фактически выполненную команду** наподобие `npm test`, `pytest -q`, `ruff check .` или `tsc --noEmit`.  Если OpenCode не помещает полную команду в `output.title`, то почти все настоящие проверки получат `isVerification: false`, и модель будет ходить по кругу с сообщением `COMPLETION BLOCKED`.[^1]

Нужно извлекать команду из аргументов tool call и сохранять её в evidence entry:

```js
function extractCommand(args = {}) {
  return String(
    args.command ??
    args.cmd ??
    args.script ??
    ""
  ).trim();
}

function isVerificationCommand(command = "") {
  const c = command.toLowerCase();

  return [
    /\b(?:npm|pnpm|yarn)\s+(?:test|run\s+(?:test|lint|check|typecheck|build))\b/,
    /\b(?:pytest|ruff|mypy|pyright|flake8|pylint|bandit)\b/,
    /\b(?:go\s+test|go\s+vet|cargo\s+(?:test|check|clippy)|gradlew?\s+test|mvn\s+test)\b/,
    /\b(?:tsc|eslint|prettier)\b/,
    /\b(?:make\s+(?:test|lint|check|build))\b/
  ].some((pattern) => pattern.test(c));
}
```

И в `tool.execute.after`:

```js
const command = extractCommand(input.args);

recordEvidence(sessionID, {
  tool: input.tool,
  title,
  command,
  // ...
  isVerification: input.tool === "bash" && isVerificationCommand(command)
});
```

В ledger лучше показывать сокращённую команду, а не только title:

```js
if (e.command) line += ` — ${e.command.slice(0, 160)}`;
```

Это будет наиболее важным исправлением перед реальным запуском.[^1]

## P1: первое сообщение получает task prompt дважды

В `system.transform` при первой генерации происходят две вещи:

1. `DISCIPLINEPROMPT`, `TASKPROMPT` и, при необходимости, `FINANCIALRULES` добавляются в блок `if (!state.fullPromptInjected)`.
2. Затем `previousTaskMode` ещё равен `null`, поэтому срабатывает блок `if (state.currentTaskMode !== state.previousTaskMode)` — и тот же task prompt плюс financial rules добавляются второй раз.[^1]

Это не ломает логику, но расходует контекст и усиливает одни и те же инструкции. Исправьте, назначив `previousTaskMode` в первом блоке:

```js
if (!state.fullPromptInjected) {
  state.fullPromptInjected = true;

  parts.push(DISCIPLINEPROMPT);

  const taskPrompt = getTaskPrompt(state.currentTaskMode);
  if (taskPrompt) parts.push(taskPrompt);

  if (needsFinancialRules(state.currentTaskMode)) {
    parts.push(FINANCIALRULES);
  }

  state.previousTaskMode = state.currentTaskMode;
} else if (state.currentTaskMode !== state.previousTaskMode) {
  const taskPrompt = getTaskPrompt(state.currentTaskMode);
  if (taskPrompt) parts.push(taskPrompt);

  if (needsFinancialRules(state.currentTaskMode)) {
    parts.push(FINANCIALRULES);
  }

  state.previousTaskMode = state.currentTaskMode;
} else {
  parts.push(DISCIPLINESHORT);
}
```

Так первый turn получит полный контракт ровно один раз, а последующие — короткую инструкцию либо delta при смене профиля.

## P1: `reasoning: max` всё ещё принудительный

Несмотря на исправления, `chat.params` всё ещё безусловно назначает `temperature`, `reasoningEffort`, а при отсутствии лимита ставит `maxOutputTokens: 8192`; почти во всех режимах выставлен `effort: "max"`, включая `default`, `coding` и `create`.[^1]

Это противоречит вашей цели использовать Coding Plan рационально: простая правка или обычный анализ будут запускаться как дорогая тяжёлая задача. Я бы сделал режим `high` дефолтом, а `max` оставил для `debug`, `audit` и финансового reconciliation:

```js
const tempMap = {
  creative: { temp: 0.7, effort: "high" },
  coding: { temp: 0.2, effort: "high" },
  create: { temp: 0.3, effort: "high" },
  debug: { temp: 0.2, effort: "max" },
  audit: { temp: 0.1, effort: "max" },
  financialverify: { temp: 0.1, effort: "max" },
  default: { temp: 0.3, effort: "high" }
};
```

Ещё лучше — не перетирать параметры, которые пользователь или агент уже указали:

```js
if (output.temperature == null) output.temperature = settings.temp;
if (output.options?.reasoningEffort == null) {
  output.options ??= {};
  output.options.reasoningEffort = settings.effort;
}
```

Сейчас плагин не адаптируется к выбранному вами вручную режиму GLM, а командует им.[^1]

## P1: режим определяется лишь одним словом

Добавление `coding` — правильное улучшение.  Но routing остался взаимоисключающим: слово `debug` победит coding, а `creative` имеет самый высокий приоритет и выключит все остальные правила.[^1]

Пример: «исправь crash в новом API и добавь тест» попадёт в `debug`, но не получит coding-правило про scoped diff и inspect existing tests. Запрос «предложи creative solution для reconciliation» попадёт в `creative`, но лишится финансовой дисциплины.[^1]

Следующий качественный шаг — хранить не один `taskMode`, а набор флагов:

```js
{
  coding: true,
  debug: true,
  financial: false,
  audit: false,
  creative: false
}
```

Для текущей версии можно сделать упрощённо: добавить coding-инструкции внутрь debug prompt, потому что большая часть debug-задач в OpenCode всё равно является кодингом.

## P2: journal по-прежнему межпроектный

Журнал по-прежнему читается из одного пути `.config/opencode/agent-journal.md`, подмешивает последние пять записей на старте сессии, а поиск ошибок работает по общим словам — `type`, `invalid`, `endpoint`, `format`, `module`.  Это не P0, но в долгой эксплуатации будет давать нерелевантные «уроки» одному проекту из другого, а также переносить служебные детали между репозиториями.[^1]

Минимальный безопасный вариант:

- Хранить journal в корне текущего workspace: `.opencode/fablize-journal.jsonl`.
- Добавлять `projectId` — например, абсолютный workspace path или его SHA-256.
- Вставлять в prompt только одну запись с совпадающим `projectId` и error signature.
- Не сохранять raw output команд, URL, токены, `.env` и request headers.
- Добавить TTL: удалять lessons старше 30–60 дней.


## P2: проверка session ID стала безопаснее, но нужна диагностика

Вы больше не используете глобальный `lastSessionID`; теперь берёте `sessionID` из `msg.info.sessionID`, и при отсутствии ID корректно пропускаете проверку. Это лучше прежнего варианта.[^1]

Но в таком случае надо добавить опциональную debug-диагностику: если реальная версия OpenCode не кладёт `sessionID` в `message.info`, completion gate будет всегда quietly skip. Например:

```js
if (!sessionID) {
  if (process.env.FABLIZE_DEBUG === "1") {
    console.error("[fablize] completion check skipped: sessionID unavailable");
  }
  return;
}
```

И протестировать именно на вашем сервере: один основной агент плюс хотя бы один subagent, одновременно работающие в разных задачах.

## Вердикт

Вы действительно устранили большую часть прежних проблем — сейчас это уже рабочий и разумный кандидат для ежедневного использования с GLM‑5.2.[^1]

Перед тем как считать версию стабильной, исправьте **P0 с `title` vs `command`** и **P1 с двойной инъекцией task prompt**. Затем добавьте 8–12 автоматических тестов на completion gate, классификацию проверочных команд, пустой ledger, две параллельные сессии и финансовый режим. Это будет уже не «плагин с хорошей идеей», а поддерживаемый механизм, который можно спокойно использовать в ваших рабочих и серверных задачах.
