P0: ledger может быть undefined
В experimental.chat.system.transform есть логика:

js
const ledger = ledgers.get(sessionID);
const hasWrites = ledger.some((e) => e.tool === "write" || e.tool === "edit");
В первой реплике сессии инструментов ещё не было, поэтому ledgers.get(sessionID) вернёт undefined. Вызов ledger.some(...) упадёт с TypeError.

Исправьте здесь и во всех похожих местах:

js
const ledger = ledgers.get(sessionID) ?? [];
const hasWrites = ledger.some(
  (e) => e.tool === "write" || e.tool === "edit"
);
То же правило нужно применить в messages.transform перед:

js
const writeInfo = countWritesInLedger(ledger);
И сделайте сами helper-функции устойчивыми:

js
function countWritesInLedger(ledger = []) {
  let count = 0;
  const files = new Set();

  for (const entry of ledger) {
    if (entry.tool === "write" || entry.tool === "edit") {
      count += 1;
      if (entry.filePath) files.add(entry.filePath);
    }
  }

  return {
    total: count,
    unique: files.size,
    files: [...files]
  };
}

function hasRiskyFileChange(ledger = []) {
  // текущая логика
}
Иначе новый функционал может тихо не работать: в messages.transform ошибка ловится пустым catch, поэтому вы увидите не явный crash, а отсутствие completion/review-логики.

P1: diff review пока декларативный
Условный diff review — правильная идея. Он запускается, если изменены три и более уникальных файла либо среди файлов есть рискованные паттерны: migration, schema, auth, api, .env, terraform, sql и т. п.

Однако state.reviewDone = true устанавливается сразу при инъекции DIFFREVIEWPROMPT, ещё до того, как модель действительно прочла diff:

js
state.pendingCompletionBlock = DIFFREVIEWPROMPT;
state.reviewDone = true;
Модель может ответить «No actionable finding after diff review», не запустив git diff, а следующий done уже не вызовет review повторно.

Сделайте два состояния:

js
reviewRequested: false,
reviewEvidenceSeen: false,
reviewDone: false
Логика:

При первом done в risky/large-diff задаче — reviewRequested = true, инъецируете review prompt.

В tool.execute.after отмечаете reviewEvidenceSeen = true, только если есть успешный bash с командой вроде git diff, git diff --check, git status --short, либо чтение изменённых файлов.

Финальный done разрешён, только если reviewEvidenceSeen === true.

Только после этого выставляете reviewDone = true.

Минимальная проверка команды:

js
function isDiffReviewCommand(command = "") {
  return /^(?:git\s+diff(?:\s|$)|git\s+status\s+--short\b)/i
    .test(command.trim());
}
И в review prompt прямо добавьте:

text
First run `git diff --check` and inspect `git diff`.
Do not state the review verdict without tool evidence.
Сейчас механизм полезен как инструкция, но ещё не как проверяемый gate.

P1: invariants нужно читать из workspace
Сейчас пути к invariants формируются через process.cwd() и глобальный ~/.opencode/fablize-invariants.md. Это может работать в вашем текущем запуске, но для project-level plugin и worktree-сценариев надёжнее использовать directory/worktree, который OpenCode передаёт контексту plugin function. Документация OpenCode прямо указывает, что плагин получает информацию о текущем проекте, рабочей директории и git worktree.

Схема лучше такая:

js
const fablizePlugin = async ({ directory, worktree }) => {
  const invariantPaths = [
    join(worktree ?? directory, ".opencode", "fablize-invariants.md"),
    join(directory, ".opencode", "fablize-invariants.md"),
    join(homedir(), ".opencode", "fablize-invariants.md")
  ];

  // return hooks
};
Это исключит ситуацию, когда глобальный плагин читает invariants не того репозитория.

P1: план пока не является контрактом
PLANCONTRACTPROMPT сам по себе хороший: Goal, scope, out of scope, acceptance checks, risks/rollback. Но planInjected ставится в true в момент, когда prompt добавлен, а не когда модель действительно вывела план. То есть пока это напоминание, не контракт.

Не нужно сразу строить сложный parser markdown. Достаточно добавить лёгкий gate:

Ставить state.planRequested = true, а не planInjected = true.

До первого write/edit искать в последнем assistant response признаки секций Goal, In scope, Acceptance checks.

Если модель пытается писать файлы без них, инъецировать:

text
PLAN REQUIRED:
Before the first file change, provide the short implementation contract:
Goal, In scope, Out of scope, Acceptance checks, Risks/rollback.
Для small coding-задач можно оставить текущий путь; включайте это только для isRisky, audit, debug и задач с несколькими затронутыми файлами.

P2: blind-spot лучше не считать выполненным заранее
blindSpotDone = true устанавливается при первом write/edit, а сам blind-spot prompt помечается как пройденный сразу после инъекции. Это означает, что модель может полностью проигнорировать pass и сразу начать менять код.

Практичный компромисс:

js
blindSpotRequested: false,
blindSpotDone: false
После инъекции ставьте только blindSpotRequested. Когда модель в следующем сообщении явно сформулировала No blocking unknowns found либо перечислила material unknowns с вариантами A/B/C — помечайте blindSpotDone.

Но это улучшение второго этапа, не причина останавливать текущий релиз.
