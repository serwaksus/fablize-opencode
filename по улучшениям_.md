Самое важное: compaction memory
Это единственное улучшение, которое я бы назвал существенным и обязательным после smoke-тестов.

В длинной сессии OpenCode неизбежно сжимает историю. Если итоговая summary создаётся обычным prompt, GLM может потерять именно то, что важно для корректного продолжения: текущую цель, инварианты, принятые решения, неизвестные, изменённые файлы, невыполненные проверки и состояние gates.

OpenCode предоставляет hook experimental.session.compacting, который позволяет добавлять доменный контекст к summary или заменить стандартный prompt compaction.

Добавьте в compaction только компактный structured state:

text
FABLIZE CONTINUATION STATE
Goal: ...
Task mode / risk: ...
Confirmed assumptions: ...
Open unknowns: ...
Implementation contract: ...
Files changed: ...
Last successful verification: command + result
Pending checks: ...
Diff review: not required | requested | evidence seen | completed
Residual risks / user decisions needed: ...
Не включайте в него весь ledger и не копируйте последние сообщения: извлекайте только факты. Это даст GLM «длинную рабочую память» без постоянного раздувания контекста — особенно полезно на удалённом OpenCode-сервере и в задачах, которые переживают много tool calls.

Самое сильное: reviewer как отдельный agent
Ваш текущий diff review просит того же автора критиковать собственный diff. Это полезно, но ограниченно: автор уже привязан к первоначальной гипотезе.

Следующий уровень — agent fablize-reviewer, которому доступны только:

задача пользователя;

implementation contract;

invariants проекта;

git diff;

результаты тестов;

список изменённых файлов.

Он не должен иметь write, edit, shell для destructive actions или доступ к секретам. Он возвращает строго структурированный список:

text
Severity: critical | high | medium | none
Finding:
Evidence: file:line
Why it matters:
Minimal remediation:
Основной агент исправляет только Critical/High, затем повторно запускает проверку. OpenCode поддерживает специализированных агентов с собственными instructions, tools и моделью, поэтому reviewer можно изолировать от исполнителя.

Включайте reviewer только для:

auth, permissions, payments, trading/orders, SQL и миграций;

public API и схем;

infrastructure/deploy;

diff от трёх файлов;

задач, где были исправлены тесты одновременно с production-кодом.

Это ближе к архитектуре planner-executor-verifier, используемой для длинных агентных задач.

Router по сложности
Сейчас task mode выбирает prompt и reasoning effort. Следующий полезный шаг — не только coding/debug/audit, а классификация сложности:

Уровень	Признаки	Режим
Fast	Один файл, ясный запрос, нет риска	GLM, high, без plan/reviewer
Standard	Несколько файлов, bugfix, тесты	GLM, high или max, contract + relevant verification
Critical	Migration, auth, production, money, API, architecture	GLM max, blind spot + contract + invariants + reviewer
Escalate	Две гипотезы провалились, неясная архитектура, reviewer нашёл Critical после двух циклов	Нужен пользователь или более сильная модель
Это реализует не «безграничное упорство», а разумную эскалацию. Fable-подход как раз строится вокруг выявления unknowns, интервью, references и planning до необратимых действий.

Для вас это важно ещё и из-за квоты: max reasoning должен быть редким и оправданным, а не использоваться для каждой небольшой правки.

Repository map
GLM слабеет не столько на написании функции, сколько на поиске правильного места в незнакомом репозитории. Добавьте custom tool repo_map:

text
repo_map(query: string) ->
  Entry points
  Relevant modules
  Public interfaces
  Test locations
  Build/test commands from package metadata
  Local conventions
Инструмент может читать только package.json, pyproject.toml, go.mod, Cargo.toml, CI configs, README и дерево верхних уровней. Результат кэшируется по git HEAD или по mtime важных manifest-файлов.

Польза: GLM перестаёт тратить несколько ходов на хаотичный поиск; решение становится более repository-aware, а расход токенов снижается без урезания reasoning. OpenCode plugins могут предоставлять модели custom tools с валидацией аргументов и собственным execution-кодом.

Реестр решений вместо journal
У вас уже есть error-context search и проектные invariants — это правильно. Следующий шаг: не свободный дневник, а versioned .opencode/decisions.md для важных решений:

text
## 2026-07-11: Email validation
- Decision: Minimal syntax validation only, no DNS lookup.
- Reason: Existing API is synchronous; external network checks are out of scope.
- Evidence: src/validators.ts, tests/validators.test.ts.
- Revisit when: Product requires deliverability verification.
Плагин должен предложить добавить запись только если модель изменила public contract, выбрала между двумя архитектурами, ввела migration или зафиксировала security/financial assumption.

При compaction или следующей задаче ищите записи только по затронутым путям/ключевым словам. Это существенно надёжнее свободного journal и предотвращает повторное обсуждение уже закрытых архитектурных решений.

Контракт тестов, а не только команда теста
Сейчас плагин проверяет, что была релевантная команда. Но это ещё не доказывает, что тест покрывает новый failure path.

Для bugfix добавьте правило:

text
If production behavior changed because of a bug:
1. Show a failing or explicitly missing scenario before the fix.
2. Add or update a test that distinguishes old behavior from new.
3. Run that focused test after the fix.
Не применяйте его к docs, formatting или чистому refactor. Для bugfix это один из самых эффективных способов приблизить GLM к качеству сильного инженерного агента: тест становится не формальностью, а доказательством, что ошибка не вернётся.
