# правки внесены

Да, две главные правки внесены корректно: проверочная команда теперь извлекается из `input.args` и сохраняется в ledger как `command`, а не определяется по UI-title; повторная инъекция task prompt на первом turn устранена через раннюю установку `previousTaskMode`.[^1]

Также улучшен контроль ресурсов: `coding`, `create`, `default` и `creative` теперь используют `reasoning: high`, а не принудительный `max`; параметры не перезаписываются, если их уже задал агент или пользователь.[^1]

## Остался один P0-блокер

В `chat.params` есть логически неверная конструкция:

```js
if (!output.maxOutputTokens) output.maxOutputTokens = 4096;
output.maxOutputTokens = 8192;
```

То есть независимо от условия финальная строка всегда ставит **8192**.  Это отменяет идею о щадящем дефолте и всегда перетирает лимит, даже если агент или пользователь уже указал, например, 1024 или 4096 токенов.[^1]

Должно быть так:

```js
if (output.maxOutputTokens == null) {
  output.maxOutputTokens = 4096;
}
```

Либо уберите управление `maxOutputTokens` целиком: это самый безопасный вариант, если GLM Coding Plan уже задаёт оптимальные лимиты через OpenCode.

## P1: слишком широкая проверка команд

`isVerificationCommand()` теперь получает реальную команду — это правильно.  Но регулярные проверки остаются чрезмерно широкими, особенно:[^1]

```js
if (/run.*(test|lint|check|verify|typecheck|build)/.test(c)) return true;
```

и:

```js
if (/python/.test(c) && /(print|sum|calc|audit|verify|check|test|range|len)/.test(c)) return true;
```

Примеры обхода:

```bash
echo "run test later"
python -c "print('verification skipped')"
```

Они могут получить статус `VERIFY`, если tool успешно завершился. Это не критично с точки зрения security, но снижает ценность completion gate: модель способна «доказать» завершение декоративной командой.[^1]

Уберите generic `run.*...` полностью и используйте более строгие паттерны начала команды:

```js
const VERIFICATION_PATTERNS = [
  /^(?:npm|pnpm|yarn)\s+(?:test|run\s+(?:test|lint|check|typecheck|build))\b/,
  /^(?:python(?:3)?\s+-m\s+pytest|pytest)\b/,
  /^(?:ruff|mypy|pyright|flake8|pylint|bandit)\b/,
  /^(?:npx\s+)?(?:tsc|eslint|prettier)\b/,
  /^(?:go\s+(?:test|vet)|cargo\s+(?:test|check|clippy)|gradlew?\s+test|mvn\s+test)\b/,
  /^make\s+(?:test|lint|check|build)\b/
];

function isVerificationCommand(command = "") {
  const value = command.trim().toLowerCase();
  return VERIFICATION_PATTERNS.some((pattern) => pattern.test(value));
}
```

Для финансового режима лучше иметь отдельную проверку: Python-команда должна не просто печатать число, а быть связана с явным анализом файла/данных. В идеале это определяется task profile, а не любым `python` с `sum`.

## P1: режимы всё ещё конфликтуют

Task mode продолжает быть одним значением с приоритетом: `creative → audit → debug → coding → create → finance`.  Поэтому:[^1]

- «исправь debug в TypeScript и добавь regression test» получит `debug`, но не `coding`;
- «создай Excel forecast и проведи reconciliation» вероятно попадёт в `create`, не в финансовый audit;
- «creative approach к reconciliation» выключит audit-ограничения полностью.

Это не блокер для запуска, но наиболее вероятная следующая причина, почему поведение GLM будет казаться непоследовательным. Лучшее решение — несколько флагов. Компромиссное — добавить coding-требования в `debug` и финансовые требования в `create`, когда запрос содержит финансовые ключевые слова.

## P1: нет очистки session state

`sessionState` и `ledgers` продолжают расти при длинной работе OpenCode: для каждой сессии создаются состояние и до 100 ledger entries, но код не очищает их после завершения сессии.  На домашнем/удалённом сервере при постоянном использовании это постепенно превратится в небольшую, но бесконечную утечку памяти.[^1]

Добавьте временную метку и TTL-очистку при любом новом hook call:

```js
const SESSION_TTL_MS = 6 * 60 * 60 * 1000;

function cleanupSessions() {
  const now = Date.now();

  for (const [id, state] of sessionState) {
    if (now - state.lastSeenAt > SESSION_TTL_MS) {
      sessionState.delete(id);
      ledgers.delete(id);
    }
  }
}

function stateOf(sessionID) {
  cleanupSessions();

  if (!sessionState.has(sessionID)) {
    sessionState.set(sessionID, {
      currentTaskMode: "default",
      previousTaskMode: null,
      pendingWarning: null,
      pendingJournalSearch: null,
      pendingCompletionBlock: null,
      fullPromptInjected: false,
      journalInjected: false,
      lastSeenAt: Date.now()
    });
  }

  const state = sessionState.get(sessionID);
  state.lastSeenAt = Date.now();
  return state;
}
```


## P2: journal не соответствует уровню других исправлений

Самая слабая часть остаётся прежней: глобальный markdown-журнал, последние пять записей в начале каждой сессии и поиск по общим словам `type`, `invalid`, `format`, `endpoint`.  Он не изолирован по проекту, может расходовать контекст и иногда импортировать неверные lessons между несвязанными репозиториями.[^1]

На этом этапе лучше **отключить автоподгрузку последних пяти записей** и оставить только узкий поиск после ошибки, пока не появятся `projectId`, структурированные JSONL-entries и TTL. Это скорее улучшит среднее качество и cache efficiency, чем ухудшит его.

## Итоговая готовность

| Область | Статус |
| :-- | :-- |
| Сессии и subagents | Почти готово: session ID больше не глобальный, но нужен TTL. [^1] |
| Completion gate | Хорошая основа: пустой ledger и write без verify блокируются. [^1] |
| Реальная проверка команд | Исправлено принципиально, но regex нужно сузить. [^1] |
| Prompt-экономия | Улучшена: нет дубля первого task prompt, обычные задачи на `high`. [^1] |
| Лимит output | **Сломан одной безусловной строкой `8192`; исправить до merge.** [^1] |
| Journal | Работает, но пока не подходит для устойчивой multi-project эксплуатации. [^1] |

После исправления `maxOutputTokens` можно уже ставить версию как рабочую. Затем я бы сделал только два небольших коммита: строгая allowlist verification-команд и session TTL. Это даст больше практической надёжности, чем дальнейшее раздувание prompt.
