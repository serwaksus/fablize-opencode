есть один оставшийся P0-логический дефект в diff review и два P1-расхождения между тем, что prompt обещает, и тем, что код реально принуждает делать.

P0: review evidence не используется
Вы добавили reviewEvidenceSeen и выставляете его, когда выполнена команда git diff или git status --short. Это верное направление.

Но в messages.transform review считается завершённым только по тексту ответа:

js
if (/no actionable finding|diff review|adversarial/i.test(fullText)) {
  state.reviewDone = true;
}
При этом state.reviewEvidenceSeen в условии не участвует. Поэтому GLM может написать:

No actionable finding after diff review.

не выполняя git diff, и reviewDone станет true. На следующем done completion будет разрешён — ровно тот обход, который вы хотели убрать.

Исправление:

js
if (state.reviewRequested && !state.reviewDone) {
  const hasVerdict =
    /no actionable finding|diff review|adversarial/i.test(fullText);

  if (state.reviewEvidenceSeen && hasVerdict) {
    state.reviewDone = true;
  }
}
И отдельно, если модель объявила verdict без evidence:

js
if (state.reviewRequested && !state.reviewEvidenceSeen && hasVerdict) {
  state.pendingCompletionBlock = [
    "DIFF REVIEW EVIDENCE REQUIRED:",
    "You stated a review verdict without inspecting the diff.",
    "Run `git diff --check` and `git diff`, then report findings with file/line evidence."
  ].join(" ");
}
Это наиболее важное исправление перед smoke-тестами. Сам DIFFREVIEWPROMPT уже требует посмотреть diff, но пока это лишь instruction, а не фактический gate.

P1: blind spot формально обходится первым write
Вы правильно начали отслеживать, был ли blind-spot pass реально сформулирован моделью через hasBlindSpotCompletion(). Но в tool.execute.after есть логика:

js
if (st.blindSpotRequested && !st.blindSpotDone) {
  st.blindSpotDone = true;
}
То есть первая запись в файл автоматически помечает blind-spot pass как выполненный, даже если модель не перечислила unknowns и не написала No blocking unknowns found.

Это безопаснее, чем бесконечно блокировать задачу, но на деле превращает gate в мягкое напоминание. Я бы не «считал его выполненным», а явно фиксировал bypass:

js
if (st.blindSpotRequested && !st.blindSpotDone) {
  st.blindSpotBypassed = true;
}
А в финальном ответе или completion gate добавлял:

text
RISK ACKNOWLEDGMENT REQUIRED:
A risky change was made before the blind-spot pass was completed.
State unknowns/assumptions and the verification performed before claiming completion.
Для вашего trading/finance/infra контекста это особенно полезно: модель может не останавливаться перед write, но не сможет тихо скрыть неразобранные риски.

P1: plan contract также не проверяется
Аналогичная ситуация у implementation plan. hasPlanMarkers() пытается найти Goal, In scope и Acceptance, что хорошо. Но после первого write код делает:

js
if (st.planRequested && !st.planProvided) {
  st.planProvided = true;
}
В результате незаполненный план считается предоставленным.

Здесь лучше отделить технический прогресс от факта плана:

js
planRequested: false,
planProvided: false,
planBypassed: false
js
if (st.planRequested && !st.planProvided) {
  st.planBypassed = true;
}
А перед итоговым done, только для risky/complex task, добавлять:

text
IMPLEMENTATION CONTRACT MISSING:
Before final completion, provide:
Goal, scope, acceptance checks, scope deviations, and residual risks.
Это не должно блокировать первый write — иначе GLM может зациклиться. Но это предотвратит ситуацию, когда агент выполнил сложную работу без зафиксированных критериев и затем заявляет, что всё завершено.

P1: git status --short недостаточен для review
isDiffReviewCommand() засчитывает git diff и git status --short как evidence review. git status --short полезен, чтобы увидеть список файлов, но он не показывает изменённые строки, контрактные поломки, небезопасные SQL-изменения или отсутствующие failure-path tests.

Рекомендую разделить evidence:

js
function isDiffListCommand(command = "") {
  return /^git\s+status\s+--short\b/i.test(command.trim());
}

function isDiffInspectionCommand(command = "") {
  return /^git\s+diff(?:\s|$)/i.test(command.trim());
}
И разрешать reviewDone только после isDiffInspectionCommand, а не после git status --short.

Оптимальная обязательная пара для risky/large diff:

bash
git diff --check
git diff
Первая ловит пробелы/форматные дефекты, вторая даёт модели материал для настоящего ревью.

Вердикт
Это уже сильная версия — примерно 9/10 как процессная надстройка для GLM‑5.2. Она реально способна уменьшить три типичных слабости агентного кодинга: преждевременное «готово», отсутствие теста после правки и неконтролируемый scope.

Перед пятью ручными сценариями я бы обязательно внёс только один короткий патч: использовать reviewEvidenceSeen при выставлении reviewDone и требовать именно git diff, а не один git status --short. После этого можно спокойно начинать smoke-тесты; plan/blind-spot bypass лучше оставить следующим небольшим улучшением, чтобы не превратить релиз в бесконечную доработку.
