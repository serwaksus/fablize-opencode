# это все, что ты можешь дать по улучшениям?

Нет. Мой прошлый ответ был только про упаковку `package.json`; это примерно 5% ценности аудита. В самом `index.js` есть сильная идея, но также несколько **архитектурных дефектов**, из-за которых плагин может не улучшать GLM‑5.2, а добавлять токены, ложные срабатывания и путаницу между сессиями.[^1]

## Главное заключение

У вас уже не «просто промпт»: есть evidence ledger, динамические режимы задачи, журнал уроков, реакция на ошибки и блокировка раннего завершения. Это хорошая основа именно для модели, которая склонна слишком рано объявлять работу завершённой.[^2][^1]

Но для приближения к Fable 5 я бы **сначала упростил и сделал правила контекстными**, а не добавлял новые. Сейчас основной prompt объединяет 10 универсальных правил: требование Python для арифметики, единицы измерения для каждого числа, две гипотезы, две попытки перед `BLOCKED`, обязательный журнал и self-rating R1/R6/R7/R8 — даже когда задача является обычной правкой кода.  Это создаёт ненужное давление на GLM и может ухудшать скорость, естественность и качество кода.[^1]

## Обязательно исправить

### 1. Изолировать состояние по сессиям

Эти переменные сейчас глобальные на весь экземпляр плагина:

```js
let pendingLazyWarning = null;
let currentTaskMode = "default";
let previousTaskMode = "default";
let pendingJournalSearch = null;
```

В результате параллельные сессии или subagents могут передавать друг другу режим задачи, предупреждение о «лени» либо ключевые слова ошибки. Например, ошибка `timeout` в сессии A способна подмешать journal-контекст в совершенно другой запрос сессии B. Это критический логический баг для OpenCode с несколькими агентами.[^1]

Замените одиночные переменные на `Map` по `sessionID`:

```js
const sessionState = new Map();

function stateOf(sessionID) {
  if (!sessionState.has(sessionID)) {
    sessionState.set(sessionID, {
      currentTaskMode: "default",
      previousTaskMode: null,
      pendingLazyWarning: null,
      pendingJournalSearch: null
    });
  }
  return sessionState.get(sessionID);
}
```

Во всех hooks работайте через `const state = stateOf(input.sessionID)`. Добавьте очистку состояния при завершении сессии, если API OpenCode предоставляет соответствующий hook; иначе ограничьте map по времени/размеру.

### 2. Не заставлять GLM исполнять финансовые правила на coding-задачах

В `DISCIPLINEPROMPT` финансовые требования глобальны: «арифметика свыше 100 — только Python», «каждое число — с единицами», «всегда показывай формулу конверсии».  Для вашей финансовой аналитики эти правила отличные, но при разработке они создают абсурдные ответы вроде обязательного указания единиц для номера порта, номера HTTP-статуса, timeout, версии пакета, количества тестов и строк в diff.[^1]

Разделите правила:

- **Core**: проверка перед `done`, честный `BLOCKED`, минимальный diff, повторный тест после исправления.
- **Debug**: reproduce → гипотезы → доказательство причины → rerun.
- **Financial**: Python/calculator, units, conversions, cell references и reconciliation.
- **Audit**: источник, контрольные суммы, полный trace расхождений.
- **Create**: readback, тесты, проверка результата.

То есть Rule 6–9 инъецируйте только в `audit`, `financialverify`, `financialanalyze`, `financialhypothesis`. Сейчас task-specific prompts существуют, но базовый full prompt всё равно навязывает финансовые правила всем сессиям.[^1]

### 3. Исправить anti-laziness

Ваш `detectLaziness()` считает словами «лени» фразы `I'll run`, `let me check`, `I will verify`.  Но это нормальные фразы **до tool call**: агент может сообщить намерение, а затем сразу вызвать инструмент в том же assistant turn. Текущий `messages.transform` видит сообщение, и если структура tool-part определена немного иначе, будет ложное предупреждение на следующий ход.[^1]

Лучше ловить не намерение, а **необоснованное финальное утверждение** без tool calls:

```js
const UNSUPPORTED_DONE = [
  /\b(done|fixed|implemented|resolved|complete)\b/i,
  /\b(готово|исправлено|реализовано|решено)\b/i
];

function hasUnsupportedCompletion(text, hasToolCall, ledgerSize) {
  return !hasToolCall &&
    ledgerSize === 0 &&
    UNSUPPORTED_DONE.some((re) => re.test(text));
}
```

А «обещание без выполнения» фиксируйте только если следующее сообщение пользователя пришло после такого ответа и сессия действительно не содержит соответствующего tool action. Это снизит ложные срабатывания и избыточные циклы. Ваш README заявляет prevention именно преждевременного завершения, а не запрет на естественную речь агента.[^2][^1]

### 4. Не перезаписывать параметры модели без согласия

Hook `chat.params` всегда назначает temperature и reasoning effort на основе keyword detection, а `maxOutputTokens` принудительно ставит в 8192, если значение отсутствует.  Это опасно по трём причинам:[^1]

- Слово `error` в пользовательском сообщении включит `debug` + `effort: max`, даже если это небольшой вопрос.
- `create` включит `max` для банальной генерации одного файла.
- Настройка OpenCode/провайдера и выбранный вами режим GLM может неявно перетираться плагином.

Это не должно быть default-поведением. Сделайте режимы **opt-in** через конфиг:

```json
{
  "fablize": {
    "adaptiveParams": false,
    "defaultProfile": "coding",
    "profiles": {
      "debug": { "temperature": 0.2, "reasoningEffort": "max" },
      "coding": { "temperature": 0.2, "reasoningEffort": "high" }
    }
  }
}
```

В `chat.params` применяйте override лишь когда `adaptiveParams === true` и параметр пользователя/агента не задан явно. Для ежедневного кодинга GLM разумнее оставить `high`; `max` включать на сложный debug, architecture или миграции.

## Сильный прирост качества

### 5. Заменить keyword routing на классификацию с приоритетами

`detectTaskMode()` сейчас опирается на вхождение слов. `brainstorm` имеет высший приоритет, потом audit, debug, create, затем финансовые режимы.  Поэтому запрос «создай Excel-модель и проверь ошибку формулы» попадёт в `create`, а не в финансовую верификацию; «creative audit dashboard» — в creative и лишится audit-дисциплины.[^1]

Лучшее решение — **несколько флагов**, а не один `mode`:

```js
{
  coding: true,
  debug: true,
  financial: false,
  audit: false,
  creative: false
}
```

После этого собирайте короткий prompt из применимых блоков. Например, `debug + coding` = reproduce + минимальный fix + test rerun; `financial + audit` = control totals + source cells + units/conversions. Это намного ближе к дисциплине Fable: правила применяются к риску задачи, а не к одному ключевому слову.

### 6. Ledger должен содержать доказательство, а не названия вызовов

Сейчас в ledger попадает имя инструмента, title, до пяти «чисел» из output и флаг `ERROR`.  Для «verification grounding» этого недостаточно. Модель получает что-то вроде:[^1]

```text
1. bash — test
2. read — index.js
3. bash — lint
```

Но не понимает: **какая команда прошла**, какой тест упал, какие файлы реально менялись и есть ли незакоммиченный diff.

Добавьте нормализованное состояние доказательств:

```js
{
  command: "npm test",
  exitCode: 0,
  result: "passed",
  summary: "42 tests passed",
  path: null,
  timestamp: Date.now()
}
```

И показывайте модели только последние релевантные результаты:

- Последняя команда test/lint/typecheck/build и exit code.
- Последняя операция записи с путём файла.
- Последняя readback-проверка этого же файла.
- Ошибки, которые ещё не были закрыты успешным rerun.

Это даст больше фактического качества и **меньше токенов**, чем нынешние 10 последних разнородных tool calls.[^1]

### 7. Ввести настоящий completion gate

Сейчас механизм требует от модели самостоятельно оценить R1/R6/R7/R8 и «исправить всё, что ниже 8».  Это полезно как nudging, но модель может просто написать «R1: 10» без реального доказательства. То есть это текстовая имитация проверки.[^1]

Сильнее работает программная проверка перед финальным ответом:

- Пользователь просил изменить код → должен быть хотя бы один write/edit.
- В задаче есть код/bug/test → после последнего write должен быть успешный test/lint/typecheck либо явное объяснение невозможности.
- Пользователь просил анализ данных → должны быть read/query/calc evidence.
- Заявлен `done/fixed` → нет неразрешённого tool error после последней успешной проверки.

Если условие не выполнено, подмешивайте короткое сообщение:

```text
COMPLETION BLOCKED:
After the last file change there is no successful verification command.
Run the smallest relevant check or state exactly why it cannot be run.
```

Это одна узкая машина правил вместо 10 общих текстовых запретов.

### 8. Журнал: сделать безопасным, структурным и необязательным

Плагин при первом запросе каждой сессии добавляет пять последних записей из `.config/opencode/agent-journal.md`; при ошибках ищет до двух фрагментов, содержащих общие слова наподобие `token`, `api`, `config`, `type`, `null`.  Риски:[^1]

- Утечка содержания одной задачи в другую, в том числе фрагментов путей, бизнес-логики или секретов.
- Ложная «память»: слово `type` или `config` найдёт почти всё и приведёт к нерелевантному совету.
- Полный journal может разрастись, а модель будет наследовать старые и уже неверные паттерны.

Улучшение:

- Хранить записи JSONL со схемой: `projectHash`, `taskType`, `errorSignature`, `cause`, `fix`, `verification`, `createdAt`, `ttl`.
- Не читать записи без совпадения `projectHash`.
- Никогда не сохранять raw tool output, `.env`, токены, URL с credentials, персональные данные.
- Искать не по одиночным словам, а по нормализованной сигнатуре: `npm:MODULE_NOT_FOUND:package-name`.
- Инъецировать не последние записи, а максимум **один** релевантный verified lesson.

Это позволит journal действительно накапливать опыт, а не загрязнять контекст.

## Улучшения именно для coding

### 9. Добавить code-specific критерии готовности

В плагине сейчас сильнее покрыты finance/audit, чем код: `create` требует readback и checks, `debug` — rerun, но нет минимального coding-contract.[^1]

Добавьте `CODING_PROMPT`:

```text
CODING COMPLETION GATE
- Before editing, inspect the nearest implementation and its tests.
- Keep the diff scoped; do not refactor unrelated code.
- After the last code edit, run the smallest relevant verification command.
- For bug fixes, show the failing scenario or a regression test, then rerun it after the fix.
- Report: files changed, verification result, and any unverified risk.
- Do not claim a test passed unless its tool output shows success.
```

Это даст GLM‑5.2 больше пользы, чем правило «все числа должны иметь единицы».

### 10. Добавить риск-классы и право на остановку

Правило «перед BLOCKED обязательно две разные попытки» вредно для продакшен-операций.  Например, при SSH failure, удалении данных, работе с реальными API или торговом контуре вторая попытка может быть опасной или дорогой.[^1]

Вместо этого:

```text
Never retry automatically when the action can:
- alter production data;
- place or cancel financial orders;
- rotate/delete credentials;
- run destructive migrations;
- incur material cloud/API cost.

Ask for confirmation and report the first failure with evidence.
```

Для ваших server/trading workflows это обязательно.

### 11. Ограничить prompt-бюджет

Полная дисциплина содержит 10 больших правил; в дальнейшем на каждый вызов добавляется short prompt, ledger до 10 записей, а также часть журнала.  Это ощутимо съедает доступный контекст и может ухудшить cache hit, особенно если текст ledger постоянно меняется.[^1]

Правильная политика:

- **Первая генерация**: core prompt до 500–700 токенов.
- **Обычный tool loop**: только delta из 80–150 токенов.
- **Перед final answer**: completion gate до 100 токенов.
- Journal: 0 токенов без точного match, максимум 150–250 токенов при match.
- Не вставлять динамический ledger в system prompt после каждого tool call, если состояние не изменило требование верификации.

Ваш двухуровневый подход full/short уже движется в правильном направлении, но `DISCIPLINESHORT` всё ещё несёт десять правил в сжатом виде, включая нерелевантные финансовые.[^1]

## Что уже хорошо

- **Двухуровневая инъекция**: полный системный контракт один раз, более короткий — дальше по сессии. Это правильнее, чем повторять огромный prompt на каждом шаге.[^1]
- **Evidence ledger на `tool.execute.after`**: хорошая база для проверки «сделано только после доказательства».[^2][^1]
- **Rerun после debug-fix** и запрет ответа «должно работать» без проверки — практически наиболее полезная часть для программирования.[^1]
- **Контекстная реакция на ошибку** вместо безусловной подгрузки всей истории — хорошая идея, если сузить error signature и изолировать проекты.[^1]

После P0–P1 вы получите не просто более строгую GLM‑5.2, а более устойчивого coding-агента: он будет меньше обещать, чаще проверять результат и реже тратить контекст на неуместные ритуалы.[^2][^1]
